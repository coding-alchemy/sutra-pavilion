# 知识库结构与维护需求

- **文档版本：** v0.1
- **文档状态：** 已批准
- **创建日期：** 2026-09-05
- **修订日期：** 2026-09-05
- **适用范围：** Sutra Pavilion 知识内容的组织、阅读与维护
- **关联设计：** [知识库结构与维护设计](./2026-09-05-knowledge-base-design.md)
- **关联决策：** [使用嵌套目录作为知识库根目录](../docs/adr/0001-use-nested-directory-as-knowledge-base-root.md)

## 1. 背景

本项目用于长期积累由人工或大模型检索、汇总的知识内容，主要读者是人工维护者。短期预计只有不超过 5 个子知识库，长期可能扩展到几十个。Obsidian 是方便人工阅读和编辑 Markdown 内容的工具，不是知识内容成立或可用的前提。

项目同时允许人工维护者通过 Obsidian 编辑内容，以及唯一的自动化维护任务通过 Git 工作区整理和提交内容。两类编辑可能同时发生，但通常位于不同子知识库。

## 2. 核心目标

在不引入大规模架构的前提下，建立一个可由人舒适阅读、可由模型轻量检索、并能安全支持人工与自动化任务并行编辑不同子知识库的 Markdown 知识库。

## 3. 角色与术语

项目术语以根目录 [CONTEXT.md](../CONTEXT.md) 为准。

- **人工维护者：** 决定何时创建子知识库、内容是否过期以及如何处理编辑冲突。
- **维护任务：** 项目中唯一的自动化内容编辑者，按人工维护者要求在明确范围内更新并提交内容。
- **知识库根目录：** 项目内的 `sutra-pavilion/`，包含导航、阅读工具配置和全部子知识库。
- **子知识库：** 知识库根目录下围绕一个长期主题组织的一级资料集合。

## 4. 功能需求

### 4.1 内容边界

1. 知识库根目录必须是项目内的 `sutra-pavilion/`，不得把项目根目录作为知识内容根目录。
2. 每个子知识库必须是知识库根目录下的一级目录；子知识库名称默认使用对人友好的中文主题名，通用名称本来是英文时可以使用英文。
3. 是否创建新的子知识库由人工维护者判断，不由维护任务根据一次检索任务、单个来源或单篇文档自动决定。
4. 知识库根目录不得存放知识正文；知识正文和附件必须归属于一个子知识库。
5. 子知识库不超过 5 个时，不得强制统一其内部目录结构。出现第 6 个子知识库时，只触发结构复核，不自动套用预设层级。
6. 没有真实主题时，不得创建示例子知识库、空模板目录或占位知识文档。

### 4.2 索引与导航

1. 知识库根目录必须有 `README.md`，完整列出所有现有子知识库，并为每个子知识库提供链接和一句话范围说明。
2. 每个子知识库必须有 `README.md`，说明主题范围并提供精选知识文档导航。
3. 子知识库索引不要求穷举所有文件；需要完整检索时，模型或工具可以扫描 Markdown 文件。
4. 索引可以由人工维护者或维护任务维护，当前不得为索引增加生成脚本或机器专用清单。
5. 索引属于导航文档，不要求包含知识文档的来源和更新日期块。

### 4.3 知识文档

1. 新知识文档默认使用中文正文和对人友好的中文文件名；英文专名、标题、接口名和必要原文引用应保留原文。
2. 每篇知识文档开头必须使用 Markdown 引用块记录来源和正文最后一次实质更新日期。
3. 来源不要求一定包含链接，但必须足以重新识别材料。书籍通常至少记录书名和作者；版本、章节和页码仅在已知且有意义时记录。
4. 文首来源列表默认表示整篇文档所依据的材料。直接引文、精确数据或相互冲突的结论必须在相关位置进一步标明具体来源。
5. 可靠来源结论不一致时，文档必须保留有实际影响的分歧和各自来源；分歧影响核心结论时，维护任务必须请人工维护者决定。
6. 已有文档覆盖同一主题时，维护任务必须优先整合和更新已有文档；只有主题边界确实不同才创建新文档。
7. 内容是否过期由人工维护者判断。维护任务可以提示疑似过期及证据，但不得仅凭日期、链接失效或新检索结果自行删除或替换结论。
8. 个别子知识库可以按实际需要使用标签或 YAML frontmatter，但当前不得定义全局字段，也不得把可选元数据作为索引的唯一依据。

### 4.4 链接与附件

1. 内部链接必须使用标准 Markdown 相对链接，不得使用本机绝对路径作为知识库内部链接。
2. 允许跨子知识库链接，但链接不改变被引用文档的唯一归属，也不得以建立共享层为由复制正文。
3. 图片、PDF 等附件必须位于使用它们的子知识库内；不得建立知识库根级共享附件目录。
4. Obsidian 新建的附件默认与当前知识文档放在同一目录。
5. 移动、重命名或删除文档时，必须检查整个知识库对旧路径的引用，并修复所有已知受影响链接后才能自动提交。

### 4.5 编辑范围与自动提交

1. 项目同时允许人工维护者通过 Obsidian 编辑内容，以及维护任务通过 Git 工作区编辑内容。Obsidian 不得自动执行 Git pull、commit 或 push。
2. 维护任务开始写入前必须声明本次目标子知识库；默认一个，确有跨库更新时可以明确声明多个。
3. 目标子知识库存在未提交修改时，维护任务必须停止自动写入并请人工维护者介入。其他子知识库的未提交修改不得阻止任务继续。
4. 维护任务不得清理、格式化、暂存、提交或覆盖目标范围之外的变化。
5. 创建、删除或重命名子知识库时，知识库根索引可以作为同一次更新的明确范围。
6. 维护任务可以自动创建 Git commit，但提交前必须确认暂存文件全部位于已声明范围。commit 数量和信息格式不作强制规定。
7. 同一子知识库出现人工与自动化并行写入时，不引入锁或自动合并协议，由人工维护者介入处理。

### 4.6 阅读工具配置

1. 知识内容必须在不依赖 Obsidian 的情况下保持为可读、可链接的 Markdown 文件。
2. 项目必须跟踪知识库根目录内的最小 `.obsidian/app.json`，固定标准 Markdown 链接、相对路径和附件与当前文件同目录的行为。
3. Obsidian 的工作区状态、缓存和非必要插件配置不得进入版本控制。
4. Obsidian 配置键不是官方承诺的稳定 API；升级应用后必须通过实际创建链接和附件的行为复核配置。

### 4.7 项目级维护规则

1. 根 `AGENTS.md` 必须包含简洁的知识库维护规则，使后续维护任务能够发现并遵守本需求中的范围、来源、链接、附件、过期判断和提交约束。
2. 外部 Skill 只有实际进入维护流程时才追加到 `AGENTS.md`；当前不得建立 Skill 注册表、适配层或预留架构。
3. 项目根 `README.md` 必须说明项目用途、知识库根目录和基本维护原则；知识库根 `README.md` 只承担子知识库总索引。

## 5. 非目标

本阶段不包含：

- 索引生成脚本、检索服务或模型专用数据库；
- 知识文档模板或 Obsidian Templates 插件配置；
- 统一的标签、YAML frontmatter 或子知识库内部目录 schema；
- 归档目录、内容状态机或软删除流程；
- 多个自动化维护任务、文件锁、任务队列或额外 Git worktree；
- 自动判断内容是否过期；
- 为未来 Skill 预建插件或适配框架；
- 第 6 个子知识库出现后的具体重构方案。

## 6. 假设、取舍与不确定项

1. 假设主要使用场景是人工阅读，模型与脚本检索只需轻量文件和索引支持。
2. 假设任意时刻只有一个自动化维护任务；人工编辑可能并行发生在其他子知识库。
3. 选择精选子知识库索引而非完整文件清单，优先保证导航质量并接受完整检索需要扫描文件。
4. 选择同目录附件而非统一附件子目录，优先保持结构自由并接受文档目录中可能混有附件。
5. 选择由人工维护者判断内容是否过期，接受维护任务不能完全自主清理旧内容。
6. 当前唯一已知的不确定项是 Obsidian 升级后内部配置键可能变化；行为要求不变，但具体配置需要复核。

## 7. 直接验收标准

1. 将 `sutra-pavilion/` 作为 Obsidian Vault 打开后，可以从根 `README.md` 进入全部现有子知识库。
2. 在 Obsidian 中新建内部链接时得到标准 Markdown 相对链接；添加附件时附件与当前知识文档位于同一目录。
3. 抽查知识文档时，每篇文档开头均有引用块，包含可识别但不强制带链接的来源，以及正文最后实质更新日期。
4. 当非目标子知识库存在人工未提交修改时，维护任务仍能修改并自动提交目标子知识库，且 commit 不包含人工修改。
5. 当目标子知识库已有未提交修改时，维护任务停止自动写入并请求人工维护者介入。
6. 移动、重命名或删除文档后，知识库中不存在指向旧路径的已知失效内部链接。
7. 面对日期较早、链接失效或新旧来源分歧的内容，维护任务只提供证据并等待人工维护者决定是否过期。

文件存在、标题匹配、格式检查、测试通过、`git diff --check` 或 commit 完成只能作为辅助证据，不能替代上述用户可观察结果。

## 8. 评审门禁

本需求与关联设计获得人工维护者明确批准后，才能编写执行计划；执行计划再次获得明确批准后，才能创建知识库结构或修改实现配置与维护规则。
