# 知识库结构与维护设计

- **文档版本：** v0.1
- **文档状态：** 已批准
- **创建日期：** 2026-09-05
- **修订日期：** 2026-09-05
- **适用范围：** Sutra Pavilion 知识内容的目录、导航、编辑边界与阅读工具配置
- **上游需求：** [知识库结构与维护需求](./2026-09-05-knowledge-base-requirements.md)
- **关联决策：** [使用嵌套目录作为知识库根目录](../docs/adr/0001-use-nested-directory-as-knowledge-base-root.md)

## 1. 设计目标

以最少的目录约定和配置满足三项核心行为：人工能够直接阅读和导航 Markdown 内容；模型能够借助索引和文件扫描定位内容；人工与唯一维护任务能够并行编辑不同子知识库而不相互提交或覆盖。

## 2. 基线与既有约束

### 2.1 当前基线

- 项目根目录已有 `AGENTS.md`、`README.md`、`.gitignore`、`docs/`、`specs/`、`src/`、`tests/` 和空的 `sutra-pavilion/`。
- 项目根 `README.md` 当前只有项目标题；知识库根目录尚无内容。
- `docs/adr/`、`specs/` 和 `specs/plans/` 已存在但此前没有 ADR、规格或计划。
- 当前没有知识文档、索引生成器、检索脚本或实现代码。
- `.gitignore` 已声明项目根不是内容 Vault，忽略项目根 `.obsidian/`，并只允许跟踪 `sutra-pavilion/.obsidian/app.json`。

### 2.2 影响设计的既有接口和限制

- 根 `AGENTS.md` 要求需求和设计位于 `specs/`，并实行“规格批准后写计划、计划批准后改实现”的人工门禁。
- `docs/agents/issue-tracker.md` 将 `specs/` 和 `specs/plans/` 定义为规格与执行任务的唯一事实源。
- Git 工作区可能包含人工维护者在非目标子知识库中的未提交修改，维护任务不能假设整个工作区干净。
- 本机 Obsidian 1.13.4 已验证 `app.json` 可控制 Markdown 链接、相对路径和附件位置，但这些 JSON 键不是官方稳定配置 API。

## 3. 目录边界

```text
项目根目录/
├── AGENTS.md
├── CONTEXT.md
├── README.md                      # 项目入口
├── docs/
│   └── adr/
├── specs/
└── sutra-pavilion/               # 知识库根目录，可作为 Obsidian Vault 打开
    ├── .obsidian/
    │   └── app.json
    ├── README.md                  # 全部子知识库索引
    ├── 子知识库甲/
    │   ├── README.md              # 精选导航
    │   ├── 知识文档.md
    │   └── 附件.ext
    └── 子知识库乙/
        ├── README.md
        └── ...
```

知识库根目录只包含工具配置、总索引和一级子知识库。每篇知识正文与附件必须位于一个子知识库中。子知识库不超过 5 个时，其内部除 `README.md` 外不规定统一目录；第 6 个子知识库出现时仅启动一次结构复核。没有真实主题时只保留根索引和必要配置，不创建示例或占位子知识库。

## 4. 导航设计

### 4.1 知识库根索引

根 `README.md` 是子知识库的完整清单，最小格式为：

```md
# Sutra Pavilion

## 子知识库

- [主题名称](./主题名称/README.md)：一句话说明范围。
```

只有创建、删除、重命名子知识库或改变其范围说明时才需要修改根索引，避免它成为所有内容更新的共享写入热点。

### 4.2 子知识库索引

子知识库 `README.md` 是人工挑选的阅读入口，最小格式为：

```md
# 子知识库名称

一句话说明该主题的长期范围。

## 导航

- [知识文档](./知识文档.md)：一句话说明内容。
```

该索引无需列出每个文件。模型需要完整发现内容时，可以扫描子知识库中的 Markdown 文件；当前不为此维护额外 manifest 或生成器。

## 5. 知识文档格式

知识文档使用中文标题和正文，必要的专有名词及原文保留原语言。文档开头使用如下最小来源块：

```md
# 文档标题

> 来源：
> - 《书名》，作者
> - [网页标题](https://example.com)
>
> 更新日期：2026-09-05
```

来源项只要求可重新识别材料，不补造未知的出版信息。文首列表表示整篇文档的总体依据；直接引文、精确数据和相互冲突的观点在正文相应位置进一步标注。索引不是知识正文，因此不使用来源块。

维护任务更新内容时优先整合已有文档。Git 保存旧版本；正文默认呈现人工维护者确认的当前理解，不建立通用归档区或版本副本。维护任务可以报告疑似过期证据，但只有人工维护者能够作出过期判断。

个别子知识库可以在确有需要时使用标签或 YAML frontmatter；当前不定义全局字段，不要求所有文档添加，也不把可选元数据作为索引的唯一依据。

## 6. 链接与附件设计

### 6.1 链接

- 内部链接使用相对于当前文档的标准 Markdown 路径。
- 跨库链接直接指向目标文档，不复制内容，也不改变目标文档归属。
- 普通内容编辑验证本次新增或修改的内部链接。
- 移动、重命名或删除文件前搜索整个知识库对旧路径的引用；需要修改的其他子知识库必须先加入本次目标范围。
- 存在已知失效内部链接时不得自动提交。

### 6.2 附件

Obsidian 使用 `Same folder as current file`，使通过 Obsidian 新增的附件与当前文档同目录。知识库根目录不允许知识正文，因此正常内容编辑不会在根目录形成无归属附件。其他编辑工具和维护任务同样必须把附件保留在所属子知识库内。

## 7. Obsidian 配置

知识库根目录只跟踪最小 `.obsidian/app.json`：

```json
{
  "useMarkdownLinks": true,
  "newLinkFormat": "relative",
  "attachmentFolderPath": "./"
}
```

该配置在本机 Obsidian 1.13.4 中分别对应关闭 Wiki Links、使用相对文件路径和附件与当前文件同目录。`.gitignore` 继续忽略 `.obsidian/` 下其他个人或设备状态。

设计约束是“产生标准 Markdown 相对链接和库内附件”，不是永久绑定上述内部键。Obsidian 升级后通过新建链接和附件直接验证行为；行为不符时更新配置并重新评审差异。

## 8. 编辑与提交协议

### 8.1 开始写入

1. 维护任务声明本次一个或多个目标子知识库，默认一个。
2. 维护任务按目标路径检查未提交修改，不以仓库整体是否干净作为前提。
3. 任一目标已有未提交修改时停止写入并请人工维护者介入；非目标路径的修改保留且不阻塞任务。

### 8.2 写入期间

1. 维护任务只读取和修改已声明目标；涉及跨库链接修复时，必须先扩大并声明目标范围。
2. 维护任务不执行仓库级清理、批量格式化或全量暂存。
3. 若人工维护者在任务期间开始修改同一目标，任务停止自动合并并请求介入。不同子知识库可以继续并行编辑。

### 8.3 验证与提交

1. 验证本次新增或修改的链接；移动、重命名和删除时验证整个知识库对旧路径的引用。
2. 只暂存明确目标路径，以及创建、删除或重命名子知识库时必要的知识库根 `README.md`。
3. 自动 commit 前检查暂存文件清单；出现范围外文件时取消提交并保留现场。
4. commit 数量和信息格式不设门禁，只要求提交范围正确且历史可理解。

这一协议利用已有子知识库边界解决最常见的并发场景，不引入锁、任务队列、分支协调或额外 worktree。

## 9. AGENTS.md 集成

后续实施只在根 `AGENTS.md` 增加一段知识库维护规则，覆盖：目标范围、脏工作区处理、来源与日期、内部链接、附件归属、人工过期判断、链接变更验证和提交范围检查。

外部 Skill 只有实际成为维护流程的一部分时才追加具体调用要求。当前不创建 Skill 目录、注册表、适配器或预留扩展点。

## 10. 直接验证

| 核心结果 | 直接验证方式 |
| --- | --- |
| 人能进入全部子知识库 | 将 `sutra-pavilion/` 作为 Vault 打开，并逐项打开根索引中的子知识库链接 |
| 链接与附件保持可移植 | 在 Obsidian 新建链接和附件，检查生成语法及实际文件位置 |
| 知识文档可回源 | 抽查知识文档开头的来源与更新日期，并验证无链接来源仍可识别 |
| 不同子知识库可以并行编辑 | 在非目标子知识库保留人工修改，让维护任务更新并提交目标子知识库，检查 commit 文件清单 |
| 同一目标不被静默覆盖 | 在目标子知识库预留未提交修改，确认维护任务停止写入并请求介入 |
| 路径变更不破坏导航 | 移动、重命名或删除文档后搜索旧路径，并逐项打开受影响链接 |
| 过期判断保留人工控制 | 给维护任务提供疑似过期材料，确认其报告证据但不自动替换结论 |

格式检查、文件存在、测试通过和 `git diff --check` 只能辅助验证，不能代替表中的直接行为。

## 11. Karpathy 精简与自检

### 11.1 假设与取舍

- 主要使用场景是人工阅读；模型与脚本支持保持轻量。
- 子知识库数量尚少，实际问题不足以证明统一内部结构有价值。
- 只有一个自动化维护任务，因此目录级范围检查足够处理预期并发。
- 人工维护者掌握内容语境，因此保留过期判断权；维护任务只提供证据。
- Obsidian 配置键可能随版本变化，因此验收稳定行为而不是把内部键当作永久接口。

### 11.2 最小方案对照

更简单的方案是把知识正文直接放在项目根目录，并只维护一个 README。该方案虽然减少一层目录和一个索引，但会把知识内容与 `specs/`、`docs/`、Agent 规则及未来工具代码混在一起，无法形成清晰的子知识库编辑边界，也不能满足从总索引进入独立主题资料集合的核心目标，因此不采用。

当前方案只增加一个嵌套知识库根、两级 README 和一个最小 `app.json`。它不要求统一子目录、完整文件清单或自动索引。

### 11.3 删除审计

设计已删除或明确排除：索引脚本、机器 manifest、知识文档模板、统一标签和 frontmatter、归档体系、自动过期判断、锁、多工作树、多任务协调、固定 commit 模板、提前设计的第 6 个子知识库结构、Skill 注册表和适配层。保留的每项规则均直接对应阅读导航、内容可回源、链接可用或并发编辑安全。

### 11.4 未批准差异

当前设计没有已知的未批准行为差异。唯一技术不确定项是未来 Obsidian 版本对内部配置键的兼容性，已通过行为复核要求处理，未改变用户要求。

## 12. 评审与后续门禁

本设计与上游需求获得人工维护者明确批准后，才能在 `specs/plans/knowledge-base/` 编写执行计划。执行计划再次获得明确批准后，才能创建知识库文件、修改 `.obsidian/app.json`、更新 README 或调整 `AGENTS.md`。
